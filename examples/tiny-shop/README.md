# The tiny shop

A working analytics project, laid out the way a Rittman Analytics engagement
lays one out. Eight tables, with one deliberate flaw per finding class.

It does two jobs. It is what the test suite scores, so any change to Hunter's
arithmetic shows up as a diff on a committed file. And it is what the
documentation shows, so anyone can see real output before installing anything.

Every name here is invented and resembles no client's.

## Run it

```bash
uv run hunter score examples/tiny-shop
uv run hunter dashboard examples/tiny-shop --out /tmp/shop.html && open /tmp/shop.html
uv run hunter align examples/tiny-shop
uv run hunter explain wh_master__customer_dim examples/tiny-shop
uv run hunter docs build examples/tiny-shop --out /tmp/example-site
```

It scores **87.8** and triggers 28 of Hunter's 77 rules across all seven scored
areas.

`hunter dashboard` writes one HTML file with the stylesheet, every chart and
the logo inlined. Only the diagram library is fetched, at a pinned version, and
the page reads in full without it.

## The two config files

Both are in [`.hunter/`](.hunter), and both are written to be read: they
document every option in comments rather than only setting the ones this example
needs.

| File | What it decides | Who edits it |
|---|---|---|
| [`.hunter/hunter.yml`](.hunter/hunter.yml) | What correct looks like: layers, naming, thresholds, weights, which rules are on | The engagement lead, rarely |
| [`.hunter/register.yml`](.hunter/register.yml) | What the team decided about particular tables: what is temporary, what is approved, who owns what | Whoever is doing the work |

**Marking a table temporary** is the register's job, not the ruleset's:

```yaml
models:
  int_shop__orders:
    persistence: temporary
    reason: a working step feeding the order fact, not for reporting from
    review_by: 2027-01-31
```

That stops the table being judged as a finished table: no consumer-facing
description expected, no owner, no key tests, and no complaint that reports do
not read from it. A reason is required because the declaration overrides what
Hunter worked out for itself, and the report says which signal decided.

Both files live at the repository root rather than inside `analytics_warehouse`,
because every path in `hunter.yml` is resolved from the root. A copy sitting
inside `analytics_warehouse` would have to say `dbt_project_dir:
analytics_warehouse` while living in that directory.

## The layout

Mirrors the standard: an `analytics_warehouse` directory holding the dbt
project, the LookML and the documentation, with the LookML manifest at the
repository root.

```
manifest.lkml                          project constants
analytics_warehouse/
  dbt_project.yml
  droughty_project.yaml
  docs/
    data_model_design/
      conceptual_model.md              the business model, written out
      conceptual_model.mermaid         the business model, drawn
      logical_model.mermaid            the data flow diagram
      physical_model.dbml              the design
    db_docs/
      tiny_shop_dbt_dev.dbml           what droughty found deployed
  models/
    field_descriptions.md              doc blocks the generated schema points at
    droughty_schema.yml                generated tests
    staging/stg_shop/
      _source.yml
      stg_shop__orders.sql
      stg_shop__customers.sql
    integration/int_shop/
      int_shop__orders.sql
    warehouse/wh_commerce/
      wh_commerce__order_fact.sql
      wh_commerce__daily_sales_xa.sql
      wh_commerce__legacy_fact.sql
      wh_commerce__forecast_fact.sql
    warehouse/wh_master/
      wh_master__customer_dim.sql
      wh_master__product_dim.sql
  lookml/
    base/_base.layer.lkml              generated views
    base/_aggregate.layer.lkml         generated measures
    staging/stg_shop.layer.lkml        hand-written labelling, as refinements
    aggregate/agg_shop.layer.lkml      hand-written measures, as refinements
    int/int_explore_shop.explore.lkml  the explores
    models/tiny_shop.model.lkml        the model file
  target/manifest.json                 generated by build.py
.hunter/
  hunter.yml                           the ruleset
  register.yml                         the recorded decisions
```

Every model is a real `.sql` file following the house shape: a `config` block
carrying the description, source CTEs prefixed `s_`, a `final` CTE, and columns
grouped by role with comments.

The LookML follows the layered structure: droughty generates `base/`, and the
`staging/` and `aggregate/` layers refine those views by hand, so regenerating
the base does not lose the labelling.

## What each table is for

| Table | Built to demonstrate |
|---|---|
| `stg_shop__orders` | Reading a source with a star and never naming a column, so the source's shape passes straight through |
| `stg_shop__customers` | Nothing. The control, and the house pattern: read with a star, then name and cast every column |
| `int_shop__orders` | A working step, declared temporary in the register |
| `wh_commerce__order_fact` | Nothing. Described, owned, keyed and tested, and marked verified in the register |
| `wh_master__customer_dim` | No description, no owner, and a key checked for uniqueness but not for being populated |
| `wh_commerce__daily_sales_xa` | No tests at all, and reading staging directly so skipping integration |
| `wh_master__product_dim` | A dimension carrying a figure, which is how a join multiplies a total |
| `wh_commerce__legacy_fact` | Built with no design, read by nothing, and naming a table directly instead of going through dbt. Marked deprecated, so it sits in the roadmap's phasing-out lane |
| `wh_commerce__forecast_fact` | Built and switched off by a project variable. Not the same as unbuilt |

Plus `wh_master__supplier_dim`, which is designed and not built, and
`package_helper`, which comes from an installed package and is reported but
never scored.

## Deliberate problems outside the models

| Where | What |
|---|---|
| `docs/data_model_design/physical_model.dbml` | Escapes a quote SQL-style (`last year''s`), which the pinned parser rejects and Hunter's normalising pass exists for |
| `docs/data_model_design/conceptual_model.mermaid` | Marks forecasts as deviating, so the claim-versus-reality check has something to compare |
| `docs/db_docs/tiny_shop_dbt_dev.dbml` | Holds columns the design does not, so the introspected comparison fires |
| `droughty_project.yaml` | Declares two overrides on one column where only one reached the generated schema |
| `models/field_descriptions.md` | Defines `supplier_pk`, which nothing references |
| `lookml/base/_base.layer.lkml` | A dimension reading `order_channel_name`, which no model produces |
| `lookml/aggregate/agg_shop.layer.lkml` | A measure duplicating a figure the warehouse already computes |
| `lookml/int/int_explore_shop.explore.lkml` | One explore with no caching policy |
| `.hunter/hunter.yml` | One rule switched off, so the divergence report has something in it |
| `.hunter/register.yml` | One temporary declaration, one verified table, one deprecated table and one silenced finding |

## Changing it

```bash
uv run python examples/tiny-shop/build.py     # rewrite the manifest from the SQL files
uv run python -m tests.regenerate_golden      # rewrite the pinned report
uv run python scripts/build_docs_pages.py     # rewrite the documented example
```

Then review all three diffs. CI fails if any of them has drifted.

`build.py` reads the SQL from the files on disk rather than carrying its own
copy, so the models and the manifest cannot disagree. It refuses to run if a
model has no file.

## What it cannot do

It cannot find a rule that is wrong, because the same person wrote the rules and
this project.

Twelve rules were wrong when first written, and every one was caught by running
against a real 280-model client repository rather than against this. Rebuilding
this example to match the real layout caught four more, which is the strongest
argument for keeping it realistic: a fixture that does not look like the real
thing does not behave like it either.

Use this to pin behaviour. Use a real repository to find out whether the
behaviour is right.
