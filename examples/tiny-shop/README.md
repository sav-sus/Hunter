# The tiny shop

A working analytics project, eight tables, with one deliberate flaw per finding
class. Small enough to read in a sitting.

It does two jobs. It is what the test suite scores, so any change to Hunter's
arithmetic shows up as a diff on a committed file. And it is what the
documentation shows, so anyone can see real output before installing anything.

Every name here is invented and resembles no client's.

## Run it

```bash
uv run hunter score examples/tiny-shop
uv run hunter align examples/tiny-shop
uv run hunter explain wh_shop__customer_dim examples/tiny-shop
uv run hunter docs build examples/tiny-shop --out /tmp/example-site
```

It scores **87.1** and triggers 28 of Hunter's 77 rules across all seven scored
areas.

## What each table is for

| Table | Built to demonstrate |
|---|---|
| `stg_shop__orders` | Taking every column from a raw source |
| `stg_shop__customers` | Nothing. The control |
| `int_shop__orders` | A working step, declared temporary in the register |
| `wh_shop__order_fact` | Nothing. Fully described, owned and tested |
| `wh_shop__customer_dim` | No description, no owner, and a key checked for uniqueness but not for being populated |
| `wh_shop__daily_sales_xa` | No tests at all, and reading staging directly so skipping integration |
| `wh_shop__legacy_fact` | Built with no design, read by nothing, and naming a table directly instead of going through dbt |
| `wh_shop__product_dim` | A dimension carrying a figure, which is how a join multiplies a total |

Plus two that exist only at some levels:

| Table | State it demonstrates |
|---|---|
| `wh_shop__forecast_fact` | Built and switched off. Not the same as unbuilt |
| `wh_shop__supplier_dim` | Designed and not built |

And `package_helper`, from an installed package, which is reported and never
scored.

## What is in here

| Path | What it is |
|---|---|
| `target/manifest.json` | Generated by `build.py`. Holds only the fields Hunter reads |
| `build.py` | Regenerates the manifest. Each table has a comment saying what it is for |
| `models/_model/shop.dbml` | The design. Six tables, four relationships |
| `docs/conceptual_model.mermaid` | The business model. Seven entities, one with no design |
| `lookml/shop.layer.lkml` | Two views, one refinement, one explore with no caching policy |
| `models/droughty_schema.yml` | Generated tests, with one override deliberately missing |
| `models/field_descriptions.md` | Five description blocks, one of them never referenced |
| `droughty_project.yaml` | The generation config, including the override that never landed |
| `.hunter/hunter.yml` | The ruleset, with one rule switched off so the divergence report has something in it |
| `.hunter/register.yml` | One temporary declaration, one silenced finding |

The design file also escapes a quote SQL-style (`last year''s`), which is what a
real repository does and what Hunter's normalising pass exists for.

## Changing it

```bash
uv run python examples/tiny-shop/build.py     # rewrite the manifest
uv run python -m tests.regenerate_golden      # rewrite the pinned report
uv run python scripts/build_docs_pages.py     # rewrite the documented example
```

Then review all three diffs. CI fails if any of them has drifted.

## What it cannot do

It cannot find a rule that is wrong, because the same person wrote the rules and
this project. Nine rules were wrong when first written and every one was caught
by running against a real 280-model repository, not by this.

Use it to pin behaviour. Use a real repository to find out whether the behaviour
is right.
